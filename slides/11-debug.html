Step Over / Step Into / Step Out の違い

Step Over (F10)

→ result = calc(x)
   # calc() の中身は見ない
→ print(result)

関数をスキップして次の行へ。中身を見る必要がない時に使う。

Step Into (F11)

→ result = calc(x)
   # calc() の中に入る!
  → def calc(x):
  →   return x * 2

関数の中に飛び込む。バグが関数内にある時に使う。

Step Out (Shift+F11)

   # 今、calc() の中にいる
  →   return x * 2
   # 呼び出し元に戻る
→ print(result)

今いる関数を抜ける。間違ってStep Inした時のリカバリ。

これが Call Stack

「今どの関数の中にいて、どこから呼ばれたか」を表示。上が現在地、下に行くほど呼び出し元。

使いどころ

  • バグの原因箇所ではなく呼び出し元が怪しい時
  • スタック内の任意のフレームをクリックしてジャンプ
  • 各フレームでの変数の状態を確認可能

条件付きブレークポイント 詳解

設定方法

行番号を右クリック → 「Add Conditional Breakpoint...」→ 条件式を入力

既存のBPを右クリック → 「Edit Breakpoint...」でも変更可能

条件式の例説明使いどころ
i == 100100回目のループで停止大量ループの特定回
data is NoneNoneの時だけ停止NoneType エラーの調査
name == "admin"特定ユーザーで停止ユーザー固有のバグ
len(items) > 1000大きなデータで停止パフォーマンス問題
response.status != 200エラーレスポンスで停止API通信のデバッグ

Log Point — コードを変えないprint

Before (print文)

for item in items:
  print(f"Processing {item.name}")
  result = process(item)
  print(f"Result: {result}")

コードを変更 → 後で削除が必要

After (Log Point)

for item in items:
  ◆ Processing {item.name}
  result = process(item)
  ◆ Result: {result}

コード変更なし → 削除も不要

Log Point の設定

行番号を右クリック →「Add Logpoint...」→ メッセージを入力
{} 内に式を書くと評価される: Processing {item.name}, count={len(items)}

Hit Count ブレークポイント

特定の回数目で停止

行番号を右クリック →「Add Conditional Breakpoint...」→ ドロップダウンで「Hit Count」を選択

入力値動作
55回目のヒットで停止
>1010回目以降のヒットで停止
%33の倍数回目で停止

使用例

# 1000回ループする処理で
# 500回目だけ調べたい
for i in range(1000):
  process(data[i])
  # Hit Count: 500
  # → 500回目で停止!

print() と デバッガの使い分け

print() が適切な場面

  • サーバーログの常時出力
  • データパイプラインの進捗表示
  • 本番環境のlogging（loggingモジュール推奨）
  • 1行だけの簡単な値確認
  • 再現が困難なタイミング依存のバグ

デバッガが適切な場面

  • 原因不明のロジックバグ
  • 複雑なデータ構造の状態確認
  • ループ内の特定条件で何が起きているか
  • 例外が発生する直前の状態
  • 他人が書いたコードの理解

結論: 両方使えることが大事。デバッガを「使える」ようになっておく

Exception ブレークポイント

例外発生時に自動停止

Breakpoints パネル →「Raised Exceptions」または「Uncaught Exceptions」にチェック。

設定説明
Raised Exceptions全ての例外で停止（try-catch内も含む）
Uncaught Exceptionsキャッチされない例外でのみ停止
User Uncaught自分のコード内のキャッチされない例外

使用場面

「エラーが出ているけど、どこで発生しているかわからない」時に最強。

TypeError: 'NoneType' has no
 attribute 'name'
→ 例外BPで発生箇所に
  自動的にジャンプ!

デバッグのベストプラクティス

1. まず仮説を立てる

「この変数が None になっているのでは?」のように予想してからデバッグ開始。闇雲にステップ実行しない。

2. バグの近くにBPを置く

エラーメッセージの行番号の少し前にBP。そこからStep Overで進めていく。

3. 二分探索デバッグ

コードの中間点にBPを置いて、バグが前半か後半か絞り込む。大きなコードベースで有効。

4. Watch式を活用

仮説に基づいた条件式をWatchに登録。True/Falseの変化を監視する。

演習1: バグを見つけよう

HANDS-ON (15分)

buggy.py
def find_average(numbers):
    total = 0
    for i in range(len(numbers) + 1):
        total += numbers[i]
    return total / len(numbers)
data = [10, 20, 30, 40, 50]
print(find_average(data))

手順

  1. 上記コードを buggy.py として保存
  2. 4行目にブレークポイントを設定
  3. F5 でデバッグ開始
  4. F10 でステップ実行
  5. Variables パネルで i を監視
  6. エラーの原因を特定
  7. 条件付きBP: i == len(numbers) を試す

演習2: 条件付きBPとLog Point

HANDS-ON (15分)

search.py
def search_users(users, query):
    results = []
    for user in users:
        if query.lower() in user["name"].lower():
            results.append(user)
    return results
users = [
    {"name": "Alice", "age": 25},
    {"name": "Bob", "age": 30},
    {"name": None, "age": 22},  # ← バグ!
    {"name": "Charlie", "age": 28},
]
print(search_users(users, "ali"))

課題1: 条件付きBP user["name"] is None で4行目に設定 → バグを特定
課題2: Log Point で「Checking user: {user['name']}」を3行目に設定 → 出力確認
